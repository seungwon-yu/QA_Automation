# 테스트 수행 가드레일

## 목적

이 문서는 자동화 테스트를 수행할 때 지켜야 할 판단 기준과 금지 사항을 정의한다.

목표는 테스트 실패를 임의로 통과 처리하지 않고, 제품 결함, 테스트 결함, 환경 오류, 판단 보류 상태를 명확히 구분하는 것이다.

## 1. 기본 원칙

테스트 수행 중에는 제품 코드, 요구사항, 기대결과, PASS/FAIL 기준을 임의로 변경하지 않는다.

테스트 실패가 발생했을 때는 실패를 없애기 위해 테스트 기준을 완화하지 않는다. 실패는 증거를 수집한 뒤 원인을 분류한다.

## 2. 금지 사항

- 테스트 중 게임 소스코드를 수정하지 않는다.
- 테스트 중 요구사항을 수정하지 않는다.
- 테스트 중 기대결과를 수정하지 않는다.
- 테스트 중 PASS/FAIL 기준을 변경하지 않는다.
- assertion 실패를 해결하기 위해 assertion 자체를 완화하지 않는다.
- 원인이 불명확한 실패를 BUG로 단정하지 않는다.
- 테스트 환경 오류를 제품 결함으로 기록하지 않는다.

## 3. 재시도 원칙

동일 조건 재시도는 최대 3회까지만 허용한다.

재시도는 다음 경우에만 수행한다.

- 브라우저 실행 지연
- 테스트 서버 응답 지연
- 일시적인 테스트 환경 불안정
- 동일 조건에서 재현성 확인이 필요한 경우

재시도 후에도 실패하면 PASS로 바꾸지 않고 실패 증거를 저장한다.

## 4. 실패 증거 저장 원칙

FAIL 발생 시 다음 증거를 저장한다.

- screenshot
- log
- state

가능하다면 다음 정보도 함께 남긴다.

- 실행 명령
- 테스트 케이스 ID
- 실패 시각
- 실행 환경
- 재시도 횟수
- 기대 결과
- 실제 결과

## 5. 실패 분류 기준

테스트 실패는 아래 중 하나로 분류한다.

| 분류 | 의미 |
| --- | --- |
| `PRODUCT_FAIL` | 제품 코드 또는 게임 동작이 기대결과를 만족하지 못한 경우 |
| `TEST_FAIL` | 테스트 코드, assertion, fixture, 하네스 사용 방식에 문제가 있는 경우 |
| `ENV_FAIL` | 서버, 브라우저, 의존성, 네트워크, 실행 환경 문제로 실패한 경우 |
| `REVIEW_REQUIRED` | 근거가 부족해 제품 결함, 테스트 결함, 환경 오류로 단정할 수 없는 경우 |

## 6. 판단 보류 원칙

원인이 불명확하면 `BUG` 또는 `PRODUCT_FAIL`로 단정하지 않는다.

판단 근거가 부족하면 `REVIEW_REQUIRED`로 종료한다.

`REVIEW_REQUIRED` 상태에서는 다음 정보를 남긴다.

- 무엇이 실패했는가
- 어떤 증거가 있는가
- 어떤 근거가 부족한가
- 다음에 확인해야 할 항목은 무엇인가

## 7. 테스트 변경 원칙

테스트가 실패했을 때 변경 가능한 것은 다음으로 제한한다.

- 증거 수집 코드 추가
- 로그 출력 추가
- 테스트 환경 설정 보정
- 테스트 케이스와 무관한 실행 안정화 작업
- 명확한 테스트 코드 결함 수정

단, 다음은 금지한다.

- 기대결과 변경
- assertion 완화
- PASS 조건 확대
- 실패 조건 제거
- 제품 코드 수정으로 테스트 통과시키기

## 8. 적용 대상

이 가드레일은 다음 작업에 적용한다.

- 하네스 테스트 실행
- 루프 엔지니어링 테스트 실행
- Playwright E2E 테스트 실행
- 테스트 리포트 작성
- 결함 보고서 작성
- 테스트 실패 분석

## 9. 테스트 결과 기록 규칙

테스트 실행 결과는 `docs/test-report.md`에 기록한다.

FAIL, `ENV_FAIL`, `TEST_FAIL`, `PRODUCT_FAIL`, `REVIEW_REQUIRED`가 발생하면 실행 명령, 증거 위치, 판단 근거를 함께 기록한다.

테스트 기준을 변경해야 할 필요가 생기면 즉시 변경하지 않고, 먼저 요구사항 또는 테스트 케이스 리뷰 대상으로 남긴다.
